## 2. 反直觉发现（每条都有实测数据，**推翻了你给的 3 条前提**）

素材：`9.2听力练习一.mp3`(944.6s/48k/立体声/192k)、`听力音频1.mp3`(845.1s/48k/立体声)、`训练1.mp3`(932.5s/44.1k/单声道/128k)、`训练2.mp3`(910.3s/44.1k/单声道)。

### 2.1 ✅【最终结论】嘀声确实存在 —— 它是**叮咚两声铃**（你自己指出的 训练1 43–46s 是决定性线索）

> 教训：我最初用三种方法（持续音调查、重复波形聚类、频谱目视）都没找到，并错误地下了“不存在”的结论。
> 它们全漏在一个原因上：**叮咚是“两声、每声都很短、快速衰减”的瞬态**，而不是持续音调。

**实测签名**（在 `训练1` 44.68 / 45.27 s 处用 4096 点 STFT 逐 100 ms 扫描得到，并目视确认）：

| 项 | 实测值 |
|---|---|
| 叮（第一声） | **2578 Hz**，峰值 −23.6 dB，起振后按指数衰减 ∼0.5 s |
| 咚（第二声） | **2039 Hz**（还有个很弱的 ∼9.9 kHz 泛音），峰值 −27.2 dB，衰减 ∼1.0 s |
| 两声间隔 | **Δ ≈ 0.59–0.60 s**（四个文件全一致） |
| 位置 | 总在**答题间隔（≥2 s 近数字静音）的末尾**，即材料分界处 |
| 电平 | 立体声素材 −16.1 / −22.8 dB；单声道素材 −21.2 / −24.8 dB |

**四个文件的检测结果（Rust 实现，直接读 mp3 原生采样率）**：

| 文件 | 叮咚对数 | 材料数 | 备注 |
|---|---|---|---|
| 9.2听力练习一.mp3 (48k 立体声) | **12** | 13 | 与 Python 基准完全一致 |
| 听力音频1.mp3 (48k 立体声) | **13** | 13 | 完全一致 |
| 训练1.mp3 (44.1k 单声道) | **17**（12 强 + 5 弱） | 13 | 包含你指的 44.7 s |
| 训练2.mp3 (44.1k 单声道) | **15** | 16 | — |

**关键收获：叮咚时刻与静音结构推出来的材料边界完全重合**（例：9.2听力练习一 的 62.46 / 94.12 / 126.12 / 151.15 / 181.49 / 208.01 / 283.57 s）。
两个独立信号互相印证 ⇒ 置信度可拉到 0.98。

**误报抑制（四个判别式，缺一不可）**：① 120 ms 内起振 ≥10 dB；② 高于 ±5 s 局部中位 ≥10 dB；
③ 峰值后 1.2 s 内**单调衰减** ≥14 dB（语音不会这样）；④ **前面必须是静音**（相对自身电平低 ≥12 dB 且 ≤−65 dB）。
初版只靠①②③ 时单文件误报 900+ 个，加上④后降到 12–17 个。

### 2.1b 已修复的两个真实 bug（供 Rust 实现参考，别再踩）
1. **瞬态泄露**：叮（2578 Hz）的起振瞬态会泄到咚（2039 Hz）频带，导致“独立检测咚”被瞬态抢走、
   反而漏掉真正 0.59 s 后的那一声。⇒ 咚**只能在“叮之后 0.25–1.2 s”窗口内找**，且取窗口内最响点。
2. **陡移累积**：帧移按采样点取整，在 44.1 kHz 下 5 ms = 220.5 → 取 221（=5.0113 ms）。
   若用**名义** 5.0 ms 做“时间→下标”换算，到 151 s 处已漂移 **340 ms**，足以把“前导静音”窗口
   滑到标记自己身上 → 系统性漏检（实测：同一文件 48k 检出 16 个、44.1k 只检出 1 个）。
   ⇒ 包络函数必须返回**真实帧移**并用它换算（`energy_envelope`/`detect_structure` 同理，
   否则 932 s 的文件末尾会漂 2 s）。

### 2.2 ❌ Whisper 的 `(bell chimes)` 不可信：那是**数字静音上的幻觉**
- 全文件转写得到 100 条 cue，其中 9 条是 `(bell chimes)`，乍看像个"嘀声检测器"。
- **但用原始采样逐条核验：9 条里有 6 条主体落在"样值恒为 0"的数字静音上**：

| cue 时间段 | 该段中"样值恒 0"占比 |
|---|---|
| 60.000–65.000s | 59.8% |
| 90.000–96.000s | 68.9% |
| 117.000–128.000s | 82.8% |
| 147.000–153.000s | 69.2% |
| 177.000–183.000s | 75.0% |
| 268.000–283.000s | **98.7%** |

- 全文件共 **84 个 ≥0.5s 的"样值恒 0"区间，合计 216.2 s = 全长的 22.9%**。另有 `(upbeat music)`、`(speaking in foreign language)` 等同类标注。
- **结论（彻底翻案）**：
  1. `(bell chimes)` 是模型在长静音上的常识性补全，**不能当文本锚点** —— 它恰好压在 10 s 答题间隔上，看起来"很准"，实际是巧合；
  2. 唯一可靠的标记信号是**静音结构本身**。

### 2.2b ❌【新发现】Whisper 的词/句时间戳在长静音处会**漂移数秒**
以"直接从 48 kHz 原始采样算出的静音地图"为基准，对照同一段音频的四种配置：

| 事实 | 值 |
|---|---|
| 真实情况（RMS 直接测量） | 片段起点后 **+2.46 s 才有声音**；+24.11→+34.12 s 是 10 s 答题间隔 |
| `-ml 1 -sow` 逐词 | 第一个词 `Have` 标在 **0.00 s**（早了 2.46 s）；后段整体偏 4 s 以上 |
| 普通模式 | 同样把 0.00 当起点（`Have you seen Jim since it happened?` 0.00→7.42） |
| `--vad` + 逐词 | `Have` 标在 **5.03 s**（晚了 2.5 s，且整句被压缩成 2.4 s） |
| `-nf -nth 0.9` | 与逐词模式完全一致，**没有改善** |

- **结论**：单靠 whisper 时间戳**不能**直接做卡拉OK 同步或切点。必须用 DSP 语音岛做
  **分段线性吸附（piecewise snapping）**：以静音地图为骨架，把每个语音岛内的词时间戳按比例映射回真实区间。

### 2.3 ✅ 静音结构极其干净（结构检测的黄金信号）
- 存在**精确数字静音**（采样值**恒为 0**，不是"小声"）：**84 个 ≥0.5s 区间 / 216.2 s / 占全文件 22.9%**。
- 单文件 0.35 s 以上静音间隙 **170–239 个**；间隙时长分布呈**两簇**：
  - **0.35–1.0 s**（大量，198+ 个）= 句子/对话轮次停顿；
  - **≥5.0 s 恰好 12 个（四个文件全一样）**= 答题间隔（含 4 个 8–12 s 与 6 个 >12 s，最长 >20 s）。
  - 1.0–2.0 s 仅 8–17 个；2–5 s 几乎为零。
- **结论**：静音/能量结构是**最可靠**的骨架来源 → 定为主依据。

### 2.8 ✅【新发现·已修复】Whisper 默认跨窗口上下文 = 长静音上的整句重复幻觉

以 `9.2听力练习一.mp3`（944.6 s）全量逐词转写（turbo q5_0，`-ml 1 -sow`）为例：

| 现象 | 实测 |
|---|---|
| 重复循环 1 | `"三个月之后,我会有十分钟的时间阅读一遍"` ×≈43，占 **80.8 s → 194.1 s** |
| 重复循环 2 | `"听话"` ×≈38，占 **268.1 s → 374.1 s** |
| 同类问题文件 | `训练1.mp3` 出现 `"the last chapter of the month."` ×17 |
| 后果 | 两个循环正好压在答题静音上，把 ~207 s 的真实对话全部顶掉 —— 这就是看到的"大量重复和错乱" |

**根因**：whisper-cli 默认 `-mc -1`（`condition_on_previous_text = true`），把上一窗口的解码文本当下一窗口的解码提示；长静音上新证据为零，模型就把提示原样续写下去，越滚越长。

**四种配置对比**（同一 944 s 音频 / 同一 16 kHz wav / 同一 turbo q5_0）：

| 配置 | 最长连续重复 | 额外重复 token（n=2..12, ≥3 次） | 944 s 耗时 |
|---|---|---|---|
| 默认 `-mc -1` | **43** | 5261 | 43.5 s |
| `-mc 64` | **59**（更糟） | 6139 | 13.3 s |
| `-mc 0` | **1** | 316（全是 `to the` 这类普通搭配） | **9.3 s** |
| `-mc 0 -sns` | 1 | 318 | 9.3 s |

**结论**：
1. **必须 `-mc 0`**（关闭跨窗口上下文）。`-mc 64` 限流不能解决问题，只有 0 能根治；
   顺带把 prompt 阶段清零，944 s 转写 43.5 s → **9.3 s**。
2. 语言不要用 `auto`：实测 `-l auto` 在这批素材上会选中文，并吐出 YouTube 字幕幻觉
   （`"请不吝点赞 订阅 转发 打赏支持明镜与点点栏目"`×6）→ 保持 `-l en`（中文提示语依然能正确转写）。
3. `-sns`（抑制非语音 token）在本文件上只改标点、无实质差别，故不启用，少一个变量。

**回归证据**：四个素材重跑（turbo + `-mc 0`），最长连续重复均为 **1**；
`--assert samples\*.mp3` 全绿；训练2 的 `Text N` 地标仍然正常检出。

**衍生工程要求（已实现）**：字幕缓存必须带**转写管线指纹**
（`asr-pipeline/2|ml=1|sow=1|mc=0|lang=en|model=<名>:<字节数>`）——
SQLite `analysis.params_hash` 存全指纹、`.limed` 的 `meta.asr_fp` 存参数指纹；
打开文件时不一致就**保留章节、丢弃字幕**，避免升级后用户继续看到
`-mc -1` 时代的重复幻觉文本。

## 4. 工程上的其他实测结论

- **Slint 1.17 没有自动换行布局**（`FlexboxLayout` 在编译器里有实现但没有作为元素暴露，`WrapLayout` 不存在）
  ⇒ 卡拉OK 的逐词折行改为 **Rust 侧估算宽度手动分行**（嵌套模型 `[[WordCell]]`）。
- **signalsmith-stretch 在 1.0x 下不透明**：开头 ~100 ms 输出高频垃圾（每 512 帧零交叉从 9.4 跳到 243–312），
  ⇒ 1.0x 走旁路，拉伸时丢弃 `output_latency + 2 块` 的预热输出。
- **cpal 回调计数是“交错样本”而位置换算是“帧”**：不加通道归一化会让可听位置被卡在 0（实测变成 0.38 倍速）。
- **whisper-cli 的 JSON 是追加扩展名**（`x.asr` → `x.asr.json`），而 `Path::with_extension` 是替换 ⇒ 找文件会失败。
- **VS 18 无法被 rustc 自动探测**（vswhere 返回空）⇒ 提供 `build.ps1` 先导入 vcvars64 再调 cargo。
- **symphonia 0.6 是破坏性重构**（`AudioCodecParameters`/`AudioSpec`/`plane`）⇒ 钉住稳定的 0.5。
